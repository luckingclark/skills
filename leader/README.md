# leader：目标任务书编制

`leader` 将原始需求整理为可交给 AI 执行者的目标任务书。它用于澄清预期结果、补充必要背景、拆解工作依赖，并规定与任务相称的交付物和完成条件。

适合研究规划、技术项目、资料整理，以及需要将本地材料转化为网页版模型可独立理解的提示词的场景。其默认输出采用严谨、清楚、自然的书面表达。

## 为什么需要明确目标

复杂任务通常同时涉及目的、资料、方法、限制与结果判断。如果只描述一个动作，执行者可能完成了某个步骤，却没有取得用户真正需要的结果。

任务书需要回答以下问题，并在必要时核验其事实基础：

| 要素 | 任务书需要说明的内容 |
|---|---|
| 目的 | 为什么开展任务，结果服务于什么需求 |
| 预期结果 | 最终应交付什么，完成后应具备什么能力 |
| 核查依据 | 如何判断结果有效，哪些内容已经实际验证 |
| 质量约束 | 哪些做法会造成表面达标而实际无效，应如何避免 |
| 工作范围 | 纳入哪些内容，存在哪些明确边界与现实限制 |
| 优先级 | 要求发生冲突时，依据什么作出取舍 |
| 不确定性 | 哪些前提待核实，缺少证据时如何继续独立部分 |

这些要素用于检查内容是否充分，不要求每次固定生成七个章节，也不强制所有任务采用相同的检查方式。

## 安装

### 由 Codex 安装

在具备技能安装能力的 Codex 对话中发送：

```text
请安装这个技能：
https://github.com/luckingclark/skills/tree/main/leader
```

安装完成并被环境识别后，使用“使用 leader”并附需求即可。其他工具应按照其自身的技能加载方式安装；本仓库不假定所有平台具有相同的安装入口或调用命令。

### 手动安装到 Codex

将本仓库中的整个 `leader` 目录复制到 `$CODEX_HOME/skills/leader`；未自定义 `CODEX_HOME` 时，通常对应用户主目录下的 `.codex/skills/leader`。这里的变量写法表示配置位置，不是一条跨操作系统通用的 shell 命令。

至少保留以下指令文件，同时保留 README 和 LICENSE：

```text
leader/
├── SKILL.md
└── references/
    ├── anatomy.md
    └── style.md
```

若已有同名技能，先比较或备份现有版本，避免覆盖自己的修改。安装是否成功，应以目标环境能够发现并读取 `leader` 及其引用文件为准。

### 配合网页版模型使用

推荐先在能够读取材料和加载技能的本地环境中，用 `leader` 编制任务书，再将完整任务书粘贴到网页版模型。

如果直接将技能指令用于不能加载技能的普通对话，需要提供 [SKILL.md](SKILL.md)、[anatomy.md](references/anatomy.md) 与 [style.md](references/style.md) 的相关内容及必要背景。只提供本地路径或技能名称，不能使网页模型获得这些内容。模型是否能联网、执行代码或生成文件，应以实际环境为准。

## 如何提供需求

最简调用方式：

```text
使用 leader，帮我描述需求、拆解目标，并整理为可直接执行的任务书。

我的需求：
……
```

可按需要补充执行平台、已有材料、期望交付物、明确约束与优先级。无需先填写完整表单；已经在当前会话中说明的信息无需重复。

### 示例一：向网页版模型交付研究任务

```text
使用 leader，将以下需求整理为可直接粘贴给网页版模型的完整研究任务书。

目标模型不能读取本地文件或技能。请先读取我提供的相关材料，
提炼必要事实、机制、参数关系、格式示例和限制，直接融入正文；
不要引用本地文件名、路径或技能名称。

请采用严谨、清楚的书面表达。
我列举的案例仅用于说明研究深度，不限制研究范围。
请先建立覆盖维度，再安排广泛检索、证据核查和实用方法整理，
并明确交付形式、完成条件及尚未解决问题的记录方式。

我的需求与材料：
……
```

### 示例二：为本地实施任务编制目标

```text
使用 leader，为以下项目需求编制目标任务书。

执行者能够访问当前工作区。
请先核对现有资料和关键接口，再说明允许修改的范围、
实施步骤、交付物、必要验证和完成条件。
将未核实信息与默认假设明确区分。
本次先编制任务书。

项目需求：
……
```

示例用于展示输入方式，不限定技能适用领域。

## 工作流程与产出

1. **识别任务与环境**：判断属于实施、研究还是混合任务，以及执行者可以访问哪些材料和工具。
2. **读取并提炼背景**：核查影响任务的事实，保留必要条件，区分已有证据、推断与待核实内容。
3. **补充必要信息**：仅询问会实质改变范围、交付或约束的缺失事项，尽量合并为一轮并控制在五项以内。
4. **组织任务书**：按依赖编排目标、步骤、交付物和核查方式，保持用户要求的广度与优先级。
5. **复核可执行性**：检查背景是否充分、示例是否误导范围、完成条件是否与实际目标对应。

通常交付一句简明使用提示和一整块可复制的 Markdown 任务书；需要时附简短核查说明。用户要求使用讲解时，可同时提供。

任务较大时，可以在同一任务书中安排分阶段或分卷交付，并保留共同目标、索引和接续摘要。篇幅根据内容需要及目标平台已核实的限制调整，不设置通用于所有平台的固定字符上限。

## 如何判断任务书是否可用

- 执行者能够理解目标并获得所需背景，不必猜测未提供的本地材料。
- 分步任务之间的输入、输出与依赖清楚。
- 范围符合原始需求，详细示例没有取代完整研究范围。
- 交付物与完成条件对应，事实、假设和未验证内容分别标明。
- 验证方法适合任务类型和变更风险；研究结论不冒充实验结果，文本审阅不冒充实际复现。

取得执行结果后，可以再次要求 `leader` 按原任务书核查覆盖、证据和可操作性。任务书编制本身不意味着已获准执行其中的计算、部署或外部操作。

## 相对于原版的主要调整

保留原版关于目标定义、必要调研、任务边界和完成证据的思路，并作出以下调整：

| 调整方向 | 当前版本的处理 |
|---|---|
| 表达方式 | 默认采用书面、准确、易读的措辞，去除角色训话、玩笑和口语化决策表达 |
| 执行环境 | 区分能够访问工作区的本地执行者与无法访问本地材料的网页模型 |
| 背景组织 | 将执行必需的资料内容与技能规则融入任务书，不以本地来源名称代替内容 |
| 示例与范围 | 示例用于校准深度或格式，除非用户明确指定，否则不作为范围边界或重点排序 |
| 广泛研究 | 按需求建立覆盖维度、补充检索、证据追溯与实用方法要求，不宣称穷尽全网 |
| 验收方式 | 分别处理实施、研究和混合任务，采用与风险相称的验证 |
| 结构与长度 | 根据任务调整章节与篇幅，不强制固定结构、指标数量或通用字符上限 |
| 连续工作 | 网页环境使用对话中的接续摘要；多执行者协作依据已有授权安排 |
